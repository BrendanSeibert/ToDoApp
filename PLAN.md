# To-Do List App — Vertical Slice Plan

A full-stack to-do list application: SolidStart backend, Neo4j database, SolidJS frontend, all runnable locally via Docker. This first pass is a **vertical slice**: minimal but complete functionality through every layer of the stack, with tests at each layer.

## Prerequisites (human-installed)

The following need to be installed on the host machine before work begins. The assistant will not install these.

- **Node.js** (LTS, v20+) and **npm** — runtime for both SolidStart backend and SolidJS frontend
- **Docker Desktop** (includes Docker Engine + Docker Compose) — for running the app and its dependencies locally
- **Git** — version control (repo will be initialized as part of this work if not already present)
- A code editor with TypeScript support (assumed already present, e.g. VS Code)

Everything else (SolidJS, SolidStart, Neo4j driver, testing libraries, Neo4j Docker image, etc.) is a project dependency and will be installed via `npm install` / pulled via Docker — no manual global installs needed beyond the above.

## High-Level Architecture

```
EX2/
├── backend/          # SolidStart server (API routes only for this slice)
│   ├── src/
│   ├── tests/
│   │   ├── unit/
│   │   └── integration/
│   ├── Dockerfile
│   └── package.json
├── frontend/         # SolidJS SPA
│   ├── src/
│   ├── tests/
│   ├── Dockerfile
│   └── package.json
├── docker-compose.yml
├── README.md
└── PLAN.md
```

- **Frontend (SolidJS)**: talks to backend via HTTP/JSON (fetch). No direct DB access.
- **Backend (SolidStart)**: exposes REST-style API routes (`/api/auth/*`, `/api/todos/*`) using SolidStart's server routes. Owns all business logic and Neo4j access.
- **Database (Neo4j)**: stores `User` and `Todo` nodes with relationships (`(:User)-[:OWNS]->(:Todo)`). Accessed only from the backend via the official `neo4j-driver` npm package.

Authentication: session-based (signed HTTP-only cookie) rather than JWT, since we control both first-party client and server and want simple, secure defaults for a v1 slice. Passwords hashed with bcrypt (or argon2) — never stored plaintext.

## Vertical Slice Scope

**In scope for this pass:**
- Register account (email + password)
- Login (creates session)
- Logout (optional but trivial — include it since login without logout is awkward)
- Delete account (while logged in, deletes user + owned todos)
- Create a todo item (text/title only)
- Mark a todo item as completed / uncompleted
- Delete a todo item
- List the logged-in user's todos (implicitly needed to render the app — not called out explicitly in the request but required to make the slice usable)

**Explicitly out of scope for this pass** (call out so nothing is assumed):
- Password reset / email verification
- Editing todo text after creation
- Due dates, priorities, tags, sharing, multi-list support
- Pagination / search
- Rate limiting, CSRF hardening beyond basics, email sending

## Data Model (Neo4j)

```
(:User {id, email, passwordHash, createdAt})
(:Todo {id, title, completed, createdAt})
(:User)-[:OWNS]->(:Todo)
```

- `User.email` has a uniqueness constraint.
- `Todo.id` and `User.id` are UUIDs generated by the backend.
- Deleting a user (`DETACH DELETE`) removes the user and all owned `Todo` nodes in one Cypher statement.

## Backend Plan (SolidStart, `/backend`)

1. **Scaffold** a SolidStart project configured as an API-only server (routes under `src/routes/api/`).
2. **Neo4j driver module** (`src/lib/neo4j.ts`): singleton driver instance, connection config from environment variables (`NEO4J_URI`, `NEO4J_USER`, `NEO4J_PASSWORD`).
3. **Auth module** (`src/lib/auth.ts`): password hashing (bcrypt), session token creation/verification, session cookie helpers.
4. **API routes**:
   - `POST /api/auth/register` — create user, reject duplicate email
   - `POST /api/auth/login` — verify credentials, set session cookie
   - `POST /api/auth/logout` — clear session
   - `DELETE /api/auth/me` — delete the logged-in user's account (and their todos)
   - `GET /api/todos` — list current user's todos
   - `POST /api/todos` — create a todo
   - `PATCH /api/todos/:id` — toggle/set completed state
   - `DELETE /api/todos/:id` — delete a todo
5. **Repository layer** (`src/lib/repositories/userRepository.ts`, `todoRepository.ts`): wraps Cypher queries, keeps route handlers thin and easy to unit test via mocking.
6. **Unit tests** (Vitest): repository logic with a mocked Neo4j driver/session; auth helper functions (hashing, session token validation); route handler logic with mocked repositories.
7. **Integration tests** (Vitest or a small custom runner), run inside Docker against a real Neo4j test container:
   - Full register → login → create todo → complete todo → delete todo → delete account flow via real HTTP calls to a running backend instance.
   - Runs via a dedicated `docker-compose.test.yml` (or a `test` profile) spinning up backend + Neo4j test instance, executed via an npm script (`npm run test:integration`).

## Frontend Plan (SolidJS, `/frontend`)

1. **Scaffold** a Vite + SolidJS SPA (no SolidStart needed here — the request specifies SolidStart for the server and plain SolidJS for the frontend).
2. **API client** (`src/api/client.ts`): thin fetch wrapper pointing at backend base URL (via env var, e.g. `VITE_API_URL`), `credentials: 'include'` for session cookies.
3. **Pages/components**:
   - `RegisterForm`, `LoginForm`
   - `TodoList` (fetches and renders todos)
   - `TodoItem` (checkbox to toggle complete, delete button)
   - `AccountSettings` or similar (delete-account action)
   - Simple router (`@solidjs/router`) with a protected route for the todo list, redirecting to login if no session.
4. **State**: a small auth/session signal/store (`src/store/auth.ts`) tracking current user; todos held in a signal within the `TodoList` component or a small store.
5. **Unit tests** (Vitest + `@solidjs/testing-library`):
   - Component rendering and interaction (e.g., submitting login form calls API client with correct payload; toggling a todo calls the right endpoint; form validation messages).
   - API client functions with mocked `fetch`.

## Docker Plan

- **`docker-compose.yml`** defines three services:
  - `neo4j` — official `neo4j:5` image, with data volume, exposed browser port (7474) and bolt port (7687), auth via env var.
  - `backend` — built from `backend/Dockerfile`, depends on `neo4j` (with healthcheck), exposes API port (e.g. 3000).
  - `frontend` — built from `frontend/Dockerfile` (Vite build served via a lightweight static server, or `vite preview`/nginx), exposes port (e.g. 5173 or 80).
- **`docker-compose.test.yml`** (or a compose profile) adds a separate Neo4j test instance + backend test runner for integration tests, isolated from the dev data volume.
- Each service has its own multi-stage `Dockerfile` (install deps → build → run).
- `.env.example` at repo root documenting required environment variables (Neo4j credentials, ports, API URL).

## Build Order (suggested execution sequence)

1. Repo scaffolding: root structure, `backend/`, `frontend/`, git init, root `README.md` stub.
2. Neo4j service in `docker-compose.yml`; confirm it starts and is reachable.
3. Backend: SolidStart scaffold → Neo4j driver module → user repository + register/login/logout/delete-account routes → unit tests.
4. Backend: todo repository + create/list/toggle/delete routes → unit tests.
5. Backend: Dockerfile → integration test harness (`docker-compose.test.yml`) → integration tests for the full flow.
6. Frontend: SolidJS scaffold → API client → auth pages/store → todo list UI → unit tests.
7. Frontend: Dockerfile → wire into main `docker-compose.yml`.
8. Full-stack smoke test via `docker compose up --build`.
9. Finalize README with verified commands.

## Open Questions / Assumptions Made

- Assuming **session-cookie auth** over JWT-in-localStorage for simpler, more secure defaults; flag if JWT is preferred instead.
- Assuming Neo4j **no auth-provider/SSO** — just email + password, since none was specified.
- Assuming todos have no per-list grouping in this slice — every todo belongs directly to the user (a single implicit list per user).
